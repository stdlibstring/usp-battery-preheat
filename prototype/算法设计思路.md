# 基于导航信息的电池充电温度预调：算法设计思路（原型版）

> 当前版本用于在官方竞赛 SDK 发放前验证算法。示例导航数据为合成测试数据，不能作为正式赛题结果。

## 1. 问题抽象

PTC 一旦开启，便以 6 kW 电功率持续运行至车辆到达充电桩。因此控制量只有一个：预热开启时刻 `t_start`，等价输出为该时刻的剩余导航距离 `start_distance`。

算法对所有候选开启时刻进行前向仿真，先过滤不满足以下硬约束的方案：

- 到达温度 `20 <= T_end <= 25 °C`；
- 到达 SOC `SOC_end >= 10%`。

随后在可行方案中同时优化充电时间和预热能耗。

## 2. 输入与输出

每个导航分段包含：

- 分段里程 `s_km`；
- 平均车速 `v_kmh`；
- 电池驱动功率 `P_drive_kW`；
- 环境温度 `T_env_C`。

输出为：

- `start_distance`：开始预热时距充电桩的距离，km；
- `T_end_opt`：到达温度，°C；
- `SOC_end_opt`：到达 SOC，%；
- `E_heat_opt`：预热电能，kWh；
- `chrg_time_s`：到达后充至 80% SOC 的时间，s。

## 3. 热-电-SOC 耦合模型

### 3.1 二维 MAP

内阻、开路电压和充电功率分别由题目给定的二维 MAP 获得。查询温度和 SOC 落在节点之间时采用双线性插值；查询值超出 MAP 时夹紧到边界，避免外推导致非物理解。

三张 MAP 的温度轴并不相同：`R_int` 和 `U_oc` 使用 20 °C 节点，`P_charge` 使用 23 °C 节点，因此分别维护温度坐标。

### 3.2 电流

总放电功率为：

```text
P_bat = P_drive + P_heat
```

Rint 模型满足：

```text
P_bat = (U_oc - I * R) * I
```

选择低电流根，并采用数值稳定的等价形式：

```text
I = 2 * P_bat / (U_oc + sqrt(U_oc^2 - 4 * R * P_bat))
```

每一步检查判别式非负。原型内部规定正电流表示放电；官方 API 返回电流的符号约定与此相反，接入时不能直接混用。

### 3.3 SOC

时间步使用秒，容量使用 Ah：

```text
SOC_pct(k+1) = SOC_pct(k) - I * dt / (C_nom_Ah * 3600) * 100
```

内部直接以百分数存储 SOC，以便与 MAP 坐标和结果通知接口保持一致。

### 3.4 温度

```text
M_bat * cp * dT/dt = I^2 * R + eta_heat * P_heat
                       - (h0 + kv * v) * (T - T_env)
```

其中 PTC 的电功率为 6 kW，进入热模型的功率乘以 0.95 转换效率。预热能耗按电气输入功率积分，单位为 kWh。

仿真采用 0.5 s 显式时间步，并在分段边界和预热开启时刻处拆分时间步，保证不会跨事件积分。

## 4. 到站充电时间

到站充电功率由终点温度和 SOC 查询 `P_charge` MAP：

```text
E_charge_kWh = max(0, (80 - SOC_end) / 100 * C_nom_Ah * U_nom / 1000)
chrg_time_s = E_charge_kWh / P_charge_kW * 3600
```

该计算遵循题目规定的“按终点状态确定全程恒定充电功率”近似。

## 5. 寻优与评分

以 1 s 为间隔枚举从出发到到达的所有预热开启时刻。每个候选方案使用 0.5 s 步长完成一次全路线仿真。

在可行方案集合内计算：

```text
Score_time = 30 * (t_max - t) / (t_max - t_min)
Score_energy = 20 * (E_max - E) / (E_max - E_min)
Score_total = Score_time + Score_energy
```

若某一指标的极差为零，则该指标对所有可行方案均给满分。总分相同时优先选择预热能耗更低的方案。

该方法没有随机性，结果可重复；对约一小时路线，C 实现仍能在很短时间内完成搜索。

## 6. 可视化与可审计性

最终最优方案重新仿真并输出 `trajectory.csv`，包含每个时间步的：

- 时间；
- 电池温度；
- SOC；
- 放电电流；
- 加热功率；
- 剩余距离。

程序生成赛题要求的五张 PNG，并在曲线上标出预热开启时刻。温度图显示 20–25 °C 目标区间，SOC 图显示 10% 安全线。

`candidate_sweep.csv` 保存所有可行候选的终点状态、两个目标和综合分，可用于复核最优解及绘制 Pareto 曲线。

## 7. 官方 SDK 接入计划

SDK 发放后进行以下替换：

1. 将插值、仿真和寻优函数移入 `student_solution.c` 的算法区域；
2. 用 `VehPwrPred_getPwrPred()` 替换 CSV 路线读取；
3. 使用 SDK 接口读取初始温度和 SOC；
4. 将四个结果接入 `BattChrgPreHeatg_ntf*` 通知接口；
5. 保留 `chrg_time_s` 供主程序打印；
6. 使用官方 Mock 库验证输出与通知值一致；
7. 使用正式导航工况重新生成曲线和最终数值。

## 8. 当前验证状态

- GCC C11 严格告警编译通过；
- MAP 节点与插值自检通过；
- 时间步、PTC 启停、终点距离和硬约束自动测试通过；
- 五张 PNG 的生成与尺寸检查通过；
- 合成工况存在可行解并完成全量候选枚举。

初始温度过低或路线过短时可能物理上不存在可行方案。此时程序明确返回“无可行解”，而不会伪造达标结果。
